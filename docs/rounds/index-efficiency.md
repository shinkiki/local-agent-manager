# 인덱스 효율 개선 회차

인덱스는 필요한 근거를 더 적은 문맥으로 전달하는 수단이다. 검색 응답이 작아졌다는 이유만으로 토큰 절감이나 품질 개선을 주장하지 않는다.

## 주제 선택과 지속성

매 회차 최근 보고에서 마지막 인덱스 평가의 커밋·측정 결과·미해결 결함을 확인한다. 인덱스 구현이나 도구 설명이 바뀌었거나, 최근 완료된 5회에 인덱스 평가가 없으면 다음 가능한 주제로 평가·개선 1건을 고른다. 보안 사고, Linux 검증 실패, 사람이 넘긴 인계가 앞서면 사유와 미완료 평가를 다음 회차에 남긴다. 평가하지 않은 것을 평가했다고 세지 않는다. 동일 주제 3회 실패 시 기존 보류 규칙을 적용하며 새 이름으로 다시 시도하지 않는다.

검색·도구 설명·파일 선택·청크·증분 갱신·오래된 결과 처리·불필요한 재조회 중 측정으로 드러난 병목 하나만 개선한다. 병렬 수, 회차 비용 상한, 보안 경계, 독립 리뷰와 검증 관문은 기존 회차 규칙을 따른다.

## 재현 가능한 기준선

`index-efficiency-cases.json`은 조정용 8건과 판정용 24건을 구분한다. 조정용으로 수정하고 판정용은 최종 검증에 사용한다. 판정 사례에 맞춰 구현을 조정했다면 해당 사례는 조정용으로 옮기고 새로운 독립 사례 20건 이상으로 판정한다. 사례를 숨기거나 실패를 제외해 수치를 높이지 않는다.

저장소의 고정된 읽기 전용 스냅샷을 `--corpus`로 사용하고 개선 전후 같은 사례·스냅샷을 쓴다. 측정 스크립트는 사례에 명시한 파일만 임시 폴더에 복사하고, 임시 HOME·앱 데이터·loopback 서버에서 실제 인덱스 MCP를 호출한다. 운영 인덱스나 사용자 권한·프로바이더 상태는 변경하지 않는다. heavy-slot 안에서 실행한다.

```sh
python3 scripts/index-efficiency-probe.py \
  --server-bin target/debug/agent-manager-server \
  --static-dir dist --corpus <고정된-저장소-스냅샷> \
  --split tuning --output .rounds/index-efficiency/tuning-before.json
# 조정용으로 개선한 뒤, 판정용 기준선과 개선본을 같은 snapshot으로 각각 실행한다.
python3 scripts/index-efficiency-probe.py \
  --server-bin <개선본-서버> --static-dir dist \
  --corpus <같은-저장소-스냅샷> --split heldout \
  --baseline .rounds/index-efficiency/heldout-before.json \
  --output .rounds/index-efficiency/heldout-after.json
```

이 탐침의 지표는 **UTF-8 전송 바이트 대리지표**다. 전체 파일 하나를 읽는 기준과 단일 검색의 요청·응답·메타데이터·MCP 도구 목록 1회를 비교한다. 실제 모델 토큰, 요금, 전체 작업의 절감률로 환산하지 않는다. 누락된 검색이 만든 작은 응답도 효율 개선으로 세지 않는다. 보고 파일에는 본문 대신 해시와 수치만 남긴다.

실제 작업의 토큰을 측정할 수 있으면 같은 모델·질문·자료·실행 조건으로 비교한다. 시스템/스킬/도구 스키마, 재시도, 추가 범위 읽기, 사용량 수집 비용을 포함하고 캐시된 입력과 일반 입력을 나눈다. 이 탐침에 없는 전체 흐름은 별도 측정으로 명시한다. 유료 호출이나 추가 의존성·사용자 권한 변경은 기존 승인 규칙을 따른다.

## 반영 기준과 보고

- 필요한 파일·근거 줄의 검색 성공률을 유지하고, 기존에 찾던 개별 사례가 누락되면 반영하지 않는다. 현재 탐침은 함수 선언 포함 여부만 검사하므로 의미적 정답·문장 근거는 별도 사례로 검증한다.
- 비밀값 저장·노출, 허용하지 않은 경로 접근, 오래된 본문 반환은 0이어야 한다. 전용 Core 회귀 시험과 실제 MCP 검증을 함께 통과한다.
- 응답 한도와 누락·부분 인덱스 상태를 숨기지 않는다. 갱신 시간·검색 지연·저장 크기를 함께 보고해 비용 전가를 확인한다.
- 기준선 대비 개선이 없으면 억지로 코드 변경을 만들지 않는다. 측정 결과와 다음 병목을 보고하고 기존 관문을 통과한 변경만 착지한다.
- 보고에 비교 커밋, corpus/case 해시, 사례 수, 개별 누락, 바이트 또는 실제 토큰의 구분, 전후 수치, 지연·저장·갱신 비용, 남은 한계를 남긴다. 다음 회차는 보고와 실제 개발선 커밋·산출물을 대조한다.
