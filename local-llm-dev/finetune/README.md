# 로컬 모델 파인튜닝 — 무엇을 가르치나

두 갈래가 있다.

1. **계획 프로토콜** (v1) — 계획 탐침의 통과 궤적으로 add_step → finish_plan, answer_now,
   cannot_do 를 굳힌다.
2. **AIA(조율자) 역할** (M11) — 전달하고 기록하고 정리하는 PO 를 가르친다. 계획·요약 같은 무거운
   일은 1티어(코덱스·클로드)에 넘기고, 조회·기록·검색은 스스로 하고, 정책은 사람에게 묻는다.
   여기에 **에이전트 매니저의 기능 지도**가 붙는다 — 219 종의 시스템 작업 이름과 인자, 그리고
   카탈로그에 **없는** 일(연결 등록·API 키)을 없다고 말하는 것까지.

둘 다 도구 이름을 외우게 하려는 것이 아니다. 실제 실행 때 모델은 카탈로그를 받아 읽으므로,
가르치는 것은 **색인에서 고르는 버릇**과 **인자 모양**이다.

CPU 레인(gpt-oss 20.9B)은 이 기계(12GB)에서 QLoRA 도 올라가지 않아 대상이 아니다.

## 파일

| 파일 | 하는 일 |
| --- | --- |
| `export-sft.mjs` | `.tuning/*trace*.jsonl` → `data/sft.jsonl`. 계획 궤적, 깨끗한 것만 |
| `export-aia-routing.mjs` | AIA 전사 → `data/routing.jsonl`. 요청을 direct·delegate·human 으로 (T1) |
| `export-aia-toolcall.mjs` | AIA 전사 → `data/toolcall.jsonl`. 성공한 시스템 MCP 호출 (T2) |
| `export-feature-map.mjs` | 카탈로그 → `data/feature-map.jsonl`. 219 종 전부 + 없는 기능 (T6) |
| `requests/feature-requests.jsonl` | 작업 219 종의 사람 말투 요청문 3개씩. 1티어가 썼다 |
| `build-aia-sft.mjs` | 위 셋 → `data/sft-aia.jsonl`. 색인을 잘라 싣고 길이를 맞춘다 |
| `setup-venv.sh` | `.venv` 에 torch(cu128)·transformers·peft·trl·bitsandbytes 를 넣는다(한 번) |
| `train_lora.py` | QLoRA 학습 → `runs/<태그>/adapter`, 병합본 `runs/<태그>/merged` |
| `generate-hf.py` | 시험 몫을 학습에 쓴 4비트 경로에서 생성해 낸다. 채점은 하지 않는다 |
| `eval-aia.mjs` | 시험 몫 채점. 서빙 층으로 묻거나 `--generated` 로 생성물을 읽는다 |
| `make-ollama.sh` | 병합본을 Ollama 에 등록. 기준 모델의 PARSER 와 PARAMETER 를 물려받는다 |
| `patches/` | llama.cpp 변환기에 덧대는 수정. GGUF 배포에 필요하다 |
| `measure.sh` | 기준 모델과 새 모델을 같은 과제·같은 n 으로 잰다 |

`.venv`·`runs/`·`data/` 는 커밋하지 않는다(gitignore). 학습 표본은 전사와 카탈로그에서 다시 낸다.

## 이 기계에서 가장 중요한 설정: 길이 2048

**2026-09-28 실측 한 스텝(Qwen3.5-9B, RTX 3080 Ti 12GB, QLoRA r=16, 그래디언트 체크포인트)**

| 토큰 | 한 스텝 |
| --- | --- |
| 256 | 4.3초 |
| 512 | 5.6초 |
| 1024 | 2.4초 |
| 2048 | 4.7초 |
| 2304 | 114초 |
| 2560 | 147초 |
| 2816 | 164초 |
| 3072 | 171초 |

1024 가 512 보다 빠른 것은 오타가 아니다. 256·512 는 고정비가 대부분이다. **절벽은 2048 과 2304
사이에 있다** — 2304 에서 이미 114초이고 VRAM 이 15.5GB 다. VRAM 이 넘치면 Windows 드라이버가 넘친 만큼을 시스템 메모리로 조용히 돌린다 — 오류가
나지 않고 그냥 느려진다. PCIe 대역이 VRAM 대역의 약 1/28 이라 행렬곱 하나하나가 20배씩 느려진다.

같은 함정을 한 번 크게 밟았다. `prepare_model_for_kbit_training` 이 노름과 출력층을 fp32 로
올리는데 이 모델 어휘가 248,320 이라 1024 자리 로짓만 fp32 로 1.0GB, 기울기까지 2.0GB 다. 그것
때문에 1024 토큰 한 스텝이 **72초**였다. fp32 층을 전부 bf16 으로 내리니 **2.4초**가 됐다(30배).
`train_lora.py` 의 `to_bfloat16` 이 그 일을 한다.

그 전에는 선형 어텐션의 torch 대체 구현을 범인으로 보고 fla Triton 커널을 끼웠다. **틀린
진단이었다** — 그 패치는 붙지도 않았고(모델 클래스가 데코레이터 시점에 함수를 잡아 둔다), 델타룰만
따로 재면 24층에 0.1초다. 느린 것을 만나면 먼저 **모양을 찍어 프로파일**한다
(`torch.profiler` 의 `record_shapes=True`). 모든 행렬곱이 **균일하게** 느리면 그것은 연산이 아니라
대역 문제다.

## 한 회차 — AIA 역할

```sh
bash local-llm-dev/finetune/setup-venv.sh                                   # 처음 한 번
cd local-llm-dev/finetune
# 카탈로그 한 벌을 받아 둔다(AIA 에게 system_catalog 를 부르게 해 결과를 저장)
node export-aia-routing.mjs "<AIA 전사 폴더>/*.jsonl" > data/routing.jsonl
node export-aia-toolcall.mjs --catalog data/system-catalog.json "<AIA 전사 폴더>/*.jsonl" > data/toolcall.jsonl
node export-feature-map.mjs --catalog data/system-catalog.json \n  --requests requests/feature-requests.jsonl > data/feature-map.jsonl
node build-aia-sft.mjs --routing data/routing.jsonl --toolcall data/toolcall.jsonl \
  --feature-map data/feature-map.jsonl --catalog data/system-catalog.json > data/sft-aia.jsonl
cd ../..
ollama stop qwen3.5-gpu-128k:latest; ollama stop gpt-oss-cpu-low:latest    # VRAM 을 비운다
local-llm-dev/finetune/.venv/Scripts/python local-llm-dev/finetune/train_lora.py \
  --data local-llm-dev/finetune/data/sft-aia.jsonl --out local-llm-dev/finetune/runs/aia-r1 \
  --epochs 2 --grad-accum 8 --max-length 2048
bash local-llm-dev/finetune/make-ollama.sh local-llm-dev/finetune/runs/aia-r1/merged qwen3.5-aia:r1
```

올라가 스텝이 수십 배 느려진다.

## GGUF 로 배포하기

Windows 의 Ollama 는 safetensors 를 가져오며 양자화할 때 MLX 를 찾는데 그것은 Apple 전용이라
없다. 양자화 없이 올리면 19GB 라 12GB 한 장에 안 올라간다. 그래서 GGUF 로 먼저 바꾼다.

llama.cpp 의 qwen3_5 변환은 **아직 병합되지 않은** PR 27132 이 있어야 한다(이슈 27019). 그
패치만으로도 부족해서 `patches/qwen3_5-ssm-alpha-beta.patch` 를 덧댄다. 두 가지를 고친다.

1. **방향** — PR 이 ssm_alpha·ssm_beta 를 한 번 더 전치해 런타임 모양 검사에서 걸린다. gguf-py 가
   shape 를 뒤집어 ne 로 적으므로 전치를 빼야 맞는다.
2. **v헤드 순서** — 다른 선형 어텐션 텐서(q·k·v·z·A_log·dt_bias·conv1d)는 전부 v헤드 재배열을
   받는데 alpha·beta 만 빠져 있었다. **이것이 조용히 모델을 망가뜨린다.**

두 번째가 훨씬 무섭다. 값의 합이 원본과 정확히 같아 유실이 없고, 모델이 로드되고 말도 되는데,
행동이 무너진다. 5회차에서 기능 호출이 학습 경로 29/30, 변환본 15/30 이었다. 재배열을 더하니
29/30 으로 붙었다. **모양 검사를 통과했다고 정렬이 맞은 것이 아니다.**

이 결함 때문에 4회차까지의 서빙 경로 수치는 전부 변환 손상이 섞인 값이다(4회차 74/94 대 학습
89/94 의 차이를 "남은 렌더링 차이"로 적었던 것은 틀렸다). 학습 경로 수치는 영향이 없다.

```sh
git clone --depth 1 --filter=blob:none --no-checkout https://github.com/ggml-org/llama.cpp
cd llama.cpp && git fetch --depth 1 origin pull/27132/head:pr27132 && git checkout pr27132
git apply <저장소>/local-llm-dev/finetune/patches/qwen3_5-ssm-alpha-beta.patch
# 양자화기는 CPU 빌드로 충분하다. 서빙은 Ollama 가 한다.
curl -LO https://github.com/ggml-org/llama.cpp/releases/download/b11222/llama-b11222-bin-win-cpu-x64.zip
<저장소>/local-llm-dev/finetune/.venv/Scripts/pip install gguf sentencepiece protobuf

python convert_hf_to_gguf.py <runs/태그>/merged --outfile aia.gguf --outtype f16 --no-mtp
./llama-quantize.exe aia.gguf aia-Q5_K_M.gguf Q5_K_M
```

### Q4_K_M 로 내리지 않는다

**이 미세조정분은 4비트에서 도구를 부르는 행동 자체를 잃는다.** 다른 조건을 전부 묶고 양자화만
달리해 같은 30건을 쟀다(2026-09-28, 컨텍스트 8192, 온도 0, 벌점 1.5, 파서 없음).

| 양자화 | 크기 | 기능 호출 | 도구를 안 부른 건 |
| --- | --- | --- | --- |
| F16 | 17.9GB | 26/30 | 0 |
| Q6_K | 6.9GB | 26/30 | 0 |
| Q5_K_M | 6.1GB | 25/30 | 1 |
| Q4_K_M | 5.3GB | 18/30 | 7 |

기반 모델은 같은 Q4_K_M 에서 멀쩡히 도구를 부른다. 양자화 일반의 문제가 아니라 LoRA 로 얹은
차이가 작아 4비트 반올림에 묻히는 것이다. **Q5_K_M 을 기본으로 쓴다** — 128k 컨텍스트로 올려도
VRAM 10GB 라 12GB 한 장에 들어간다. Q6_K 는 11GB 로 여유가 거의 없다.

이 자리를 찾는 데 네 번을 돌렸다. 파서·벌점·표본추출을 차례로 의심했는데 전부 빗나갔고, 원인은
두 가지를 한 회차에 같이 바꾼 것이었다. **변수를 하나만 남기고 나머지를 고정하면 한 번에 나온다.**

Modelfile 에 세 가지를 챙긴다.

- **`PARSER` 줄은 넣지 않는다.** 기준 모델에는 `PARSER qwen3.5` 가 붙어 있어 따라 넣고 싶어지지만,
  그것은 safetensors 로 가져온 모델의 것이다. GGUF 로 가져온 모델에 같은 줄을 넣으면 렌더링이
  어긋나 모델이 시스템 글과 요청을 되풀이한다(기능 호출 17/30 → 0/30). GGUF 는 제 안의
  `tokenizer.chat_template` 으로 돈다.
- **PARAMETER 는 하나도 빼지 않는다.** `presence_penalty` 를 빼 보고 같은 붕괴를 한 번 더 겪었다.
  요청 본문에 실은 `presence_penalty` 는 Ollama 의 OpenAI 호환 엔드포인트가 무시하므로, 이 값을
  실험하려면 Modelfile 을 바꿔 다시 등록해야 한다.
- `ollama create` 에 `-q` 를 주지 않는다. 이미 양자화된 GGUF 다.

## 부르는 쪽은 사고를 꺼야 한다

학습 표본을 빈 사고 기록으로 구웠다. 그래서 모델은 `</think>` 를 스스로
낼 줄 모른다. 사고를 켠 채로 부르면 **끝없이 생각만 한다** — 첫 배포 확인에서 8만 토큰까지 갔다.

- Ollama 네이티브: `{"think": false}`
- OpenAI 호환: `{"reasoning_effort": "none"}`

## 3회차 성적 (2026-09-28)

학습에 넣지 않은 143 건. 기준 모델과 같은 몫, 같은 채점기다.

| 과제 | 기준 | 3회차 |
| --- | --- | --- |
| 기능 호출 | 43/95 | 92/95 |
| 이름 풀이 | 5/36 | 35/36 |
| 도구 호출 | 1/12 | 3/12 |

**기능 호출이 판정이다.** 요청문을 1티어가 사람 말투로 다시 쓴 뒤라 카탈로그 설명을 베껴 맞출 수
없다. 같은 재작성 때문에 기준 모델은 오히려 떨어졌다(설명 그대로였던 1회차 19/30 = 63%, 사람
말투 43/95 = 45%). 그 어려워진 과제에서 97% 다. 설명을 외운 것이 아니라 대응을 배웠다는 뜻이다.

기준 모델의 실패 95 건 중 32 건이 "도구를 아예 안 부름"이고 19 건이 "다른 작업을 고름"이다.
3회차는 앞의 것이 0 이다.

**도구 호출 칸은 읽지 않는다.** 이 과제는 "그때 1티어가 우연히 고른 첫 호출과 같은가"를 묻는다.
여러 답이 다 맞는 요청이 대부분이라 단일 정답으로는 잴 수 없다. 사람이 확인한 기준선을 만들기
전까지 이 칸은 참고도 아니다.

**라우팅은 3회차부터 학습에서 뺐다.** 라벨을 사람이 아니라 스크립트가 도구로 매겼고, 시험 몫에서
무조건 "위임"이라 답하는 상수가 두 모델보다 나았다. 틀릴 수 있는 라벨로 정책 판단을 가르치면
고치기 어려운 버릇이 붙는다. 살리려면 사람이 라벨을 단 기준선이 먼저다.

## 4회차 — 학습 경로와 서빙 경로를 붙인다

3회차의 진짜 문제는 점수가 아니라 **두 경로가 갈린 것**이었다. 같은 가중치가 학습 렌더링에서
92/95, Ollama 렌더링에서 43/95 였다.

원인은 도구 스키마의 `required` 였다. `arguments` 를 선택으로 선언해 두었는데 정답은 늘 그 칸을
채운다. 학습 렌더링은 스키마 전체를 풀어 써서 티가 안 났고, Ollama 렌더링에서만 모델이 그 칸을
건너뛰었다. 빈 채로 닫아 `unexpected end of JSON input` 500 을 내는 건도 섞였다.

`required` 에 `arguments` 를 넣고 다시 학습했다.

| 과제 | 3회차 학습 | 3회차 서빙 | 4회차 학습 | 4회차 서빙 |
| --- | --- | --- | --- | --- |
| 기능 호출 | 92/95 | 43/95 | 89/94 | 74/94 |
| 이름 풀이 | 35/36 | 35/36 | 35/36 | 34/36 |

실패 종류가 결정적이다. 서빙 경로에서 `인자빠짐` 24 → 2, `서빙오류` 12 → 0 이다. 고치려던 자리가
정확히 닫혔다.

**학습 점수는 오르지 않았다(92 → 89).** 이 수정은 학습을 잘하게 하는 것이 아니라 서빙이 학습을
따라오게 하는 것이었다. 두 경로가 갈릴 때 가중치부터 의심하지 않는다 — **프롬프트를 양쪽에서
찍어 비교한다.** 학습 프롬프트를 raw 로 넣어 보면 같은 가중치가 제대로 답하는지 한 번에 알 수 있다.

### 그때 "설명을 읊는다"고 본 것은 오진이었다

4회차 서빙의 남은 실패를 `호출없음` 으로 보고 "기능 호출 표본과 이름 풀이 표본이 닮아 모드를
헷갈린다"고 적었다. **틀렸다.** 그 되읊음은 변환기 손상의 증상이었다.

변환기를 고치고 같은 4회차 병합본을 다시 내려 재니 기능 호출 **92/94** 다(손상된 변환본은 74/94).
학습 경로 89/94 와 붙는다. 모드 혼동은 없었다.

그 오진 때문에 5회차에서 시스템 글에 "반드시 도구를 부른다" 한 줄을 넣었는데, 값이 없었다.

| 회차 | 그 줄 | 학습 | 서빙(고친 변환기) |
| --- | --- | --- | --- |
| 4회차 | 없음 | 89/94 | 92/94 |
| 5회차 | 있음 | 91/93 | 88/93 |

넣은 쪽이 오히려 조금 낮다. 그 줄은 되돌렸다.

**증상으로 데이터를 고치기 전에 도구 사슬을 먼저 의심한다.** 모델이 이상한 글을 뱉으면 프롬프트나
표본을 손보고 싶어지지만, 그 전에 같은 가중치가 다른 경로에서도 같은 짓을 하는지 본다. 학습 경로가
멀쩡하면 문제는 데이터가 아니다.

## 5회차 — 배포 경로를 믿을 수 있게 됐다

변환기를 고친 뒤 학습 경로와 서빙 경로가 붙었다. 같은 시험 몫 141 건이다.

| 과제 | 학습 경로 | 서빙 Q5_K_M |
| --- | --- | --- |
| 기능 호출 | 91/93 | 88/93 |
| 이름 풀이 | 35/36 | 35/36 |
| 도구 호출 | 2/12 | 3/12 |

격차 3점은 양자화 몫으로 설명된다. 회차마다 두 경로가 68점씩 갈리던 것이 여기서 끝났다.

이 회차에서 바꾼 시스템 글 한 줄은 값이 없었다(4회차 절 참고). 되돌렸다. 회차의 성과는 그 줄이
아니라 변환기 결함을 잡은 것이다.

## 한 시간을 쓰기 전에 먼저 잰다

프롬프트 문장을 바꾸려 할 때는 **학습하지 않고 그 문장만 붙여 이미 있는 모델에 물어본다.** 한
회차가 학습 1시간, 생성 40분이라 문장 하나를 확인하려고 그것을 쓰는 것은 낭비다.

5회차 예: "반드시 도구를 부른다" 한 줄을 4회차 모델의 시스템 글에 붙여 30건을 다시 물었다.
호출없음이 4 → 2 였다. 그 문장이 행동을 움직인다는 것을 5분에 확인하고 학습에 넣었다.

움직이지 않으면 학습에 넣어도 대개 움직이지 않는다. 데이터 쪽을 봐야 한다는 신호다.

**한 회차에 한 가지만 바꾼다.** 이 규율을 어겨 세 번 헤맸다(파서와 벌점을 같이 바꾼 자리,
스키마와 표본을 같이 바꿀 뻔한 자리). 둘을 같이 바꾸면 어느 쪽이 들었는지 알 수 없고, 되돌릴
때도 무엇을 되돌려야 하는지 모른다.

## 좁게 가르치면 원래 하던 것을 잊는다

**5회차까지 만든 모델은 런타임에서 쓸 수 없다.** 사용자가 실제 반복요청에 붙여 보고 드러났다.

계획 탐침으로 재니 숫자가 분명하다(과제당 10회).

| 과제 | 기준 모델 | 튜닝 r4 |
| --- | --- | --- |
| 불가능 판정 | 10/10 | 4/10 |
| 웹에서 노션으로 | 10/10 | 1/10 |
| 로컬 파일 읽기 | 9/10 | 5/10 |

웹에서 노션으로가 1/10 이다. 계획에 필요한 도구 자리를 아예 만들지 않는다 — 노션 만들기 자리가
아홉 번, 웹 가져오기 자리가 세 번 빠졌다. 실기기 반복요청에서는 요청과 무관한 중국어 단계 제목을
세우고 없는 경로에 bash 를 부르는 것까지 봤다.

학습 데이터 717 건이 전부 단발 도구 호출이고 계획 프로토콜은 한 건도 없다. 좁은 형식만 집중해서
가르치니 원래 하던 계획 세우기를 잊었다.

**이 실패는 절차가 이미 경고하고 있었다.** "학습에 없는 과제가 판정이다", "판단 측정은 실행 측정을
대신하지 못한다" — 둘 다 이 안내서와 튜닝 회차 스킬에 적혀 있는데 다섯 회차를 돌면서 계획 탐침을
한 번도 돌리지 않았다. **회차마다 계획 탐침을 판정에 넣는다.**

### 계획 표본을 섞는 길은 이 기계에서 막혀 있다

계획 궤적은 한 건이 2,594~3,076 토큰이다. 위 표의 절벽 너머다. 섞으면 AIA 표본까지 그 길이로
패딩돼 학습이 87시간이 된다. 고정 길이 패딩을 걷어내도 계획 표본 한 건에 100초 넘게 든다.

남은 손잡이는 **학습량**이다. 망각은 양에 비례하므로 에포크·학습률·LoRA 계수를 낮춰 본다.

### 에포크는 손잡이가 아니었다 (6회차)

에포크만 2 → 1 로 내렸다. 계획은 거의 안 돌아오고 AIA 쪽만 잃었다.

| 과제 | 기준 | 2에포크(r4) | 1에포크(r6) |
| --- | --- | --- | --- |
| 계획 합계 | 29/30 | 10/30 | 12/30 |
| 계획 web-to-notion | 10/10 | 1/10 | 0/10 |
| 기능 호출 | 43/95 | 92/94 | 82/93 |

web-to-notion 이 여전히 0 이다. 여러 도구를 잇는 계획을 아예 세우지 못한다. **양의 문제가 아니라
형식 충돌이다** — AIA 표본은 "system_read 를 정확히 한 번 부른다"를 727 번 가르치는데, 계획
프로토콜은 "plan_add_step 을 여러 번 부르고 finish_plan 으로 닫는다"이다. 학습 데이터에 후자가
한 건도 없으니 전자가 그 자리를 덮는다.

### 용량도 손잡이가 아니었다 (7회차)

LoRA 계수만 16 → 4 로 내렸다. 학습 가능한 파라미터가 29M 에서 7M 으로 줄었다.

| 과제 | 기준 | r4 계수16 | r6 1에포크 | r7 계수4 |
| --- | --- | --- | --- | --- |
| 불가능 판정 | 10/10 | 4/10 | 6/10 | 9/10 |
| 웹에서 노션으로 | 10/10 | 1/10 | 0/10 | 1/10 |
| 로컬 파일 읽기 | 9/10 | 5/10 | 6/10 | 1/10 |
| 계획 합계 | 29/30 | 10/30 | 12/30 | 11/30 |
| 기능 호출 | 43/95 | 92/94 | 82/93 | 82/93 |

불가능 판정은 9/10 으로 거의 돌아왔는데 로컬 파일 읽기가 5 → 1 로 무너졌다. 합계는 그대로고 AIA
쪽만 10점 잃었다.

**학습량을 줄이는 두 방법이 모두 실패했다.** 용량을 조여도 본 적 없는 형식이 돌아오지는 않는다.
모델이 계획 프로토콜을 **보아야** 한다.

### 섞는다 (8회차)

계획 표본 48 건을 AIA 표본 717 건에 섞는다. 나머지는 가장 좋았던 r4 설정 그대로다(계수 16,
2에포크). 계수와 에포크를 낮추는 것이 둘 다 손해였으니 되돌렸다.

전부 넣지 않는 이유는 길이다. 계획 표본은 2,594~3,076 토큰이라 절벽 너머이고 한 건에 100초 넘게
든다. 192 건이면 2에포크 17시간, 48 건이면 5시간이다. 목적이 **가르치는 것이 아니라 잊지 않게
하는 것**이라 몇십 건으로 충분한지 먼저 본다.

## 판정 — 합격률이 아니라 실패 종류

- **학습에 든 과제**는 외워서 맞출 수 있다. 그 수치는 참고만 한다.
- **학습에 없는 과제**가 판정이다. 새 모델이 여기서 새로운 실패 종류를 내면 되돌린다 —
  프로토콜을 배운 것이 아니라 답을 외운 것이다.
- AIA 역할은 라우팅 정확도만으로 재지 않는다. 위임한 뒤 **결과를 가져와 확인하는지**, 요약을
  스스로 쓰지 않는지가 같이 걸린다.
- 통과해도 운영 연결의 기본 모델을 바꾸지 않는다. 새 태그를 **다른 연결 이름**으로 두고 사람이
  고른다(M7 연결 목록). 모델 교체는 사람이 정한다.

## 알려진 한계

- 계획 추적본은 계획 턴만 담는다. 단계 실행·종합 턴은 학습하지 않는다.
- AIA 전사는 개발 작업에 치우쳐 있다(위임 192 대 직접 40). `--max-per-label` 로 잘라 맞추지만,
  실제 운영 사용이 쌓여야 균형이 잡힌다.
- 기능 지도 요청문은 1티어 에이전트 여섯이 나눠 썼다(`requests/feature-requests.jsonl`). 다시
  만들면 문장이 달라지므로 커밋해 두고, 카탈로그에 작업이 늘면 그 몫만 더 쓴다.
- 기본 계정 지정과 활성 계정 전환은 카탈로그 설명이 서로 "같음"이라 의미로 가를 수 없다. 요청문을
  갈라 두었지만 학습에서 혼동될 쌍이다. 고치려면 앱 쪽 설명을 손봐야 한다.
- Ollama 의 safetensors 가져오기(qwen3.5 아키텍처)가 안 되면 llama.cpp 변환으로 돌아간다.
