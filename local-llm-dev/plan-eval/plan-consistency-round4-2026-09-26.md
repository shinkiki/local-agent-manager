항상 거절되는 도구여서 조사 단계만 확정했다. 현행 19회차의 노션 검색·수정에서도

수락된 계획으로 혼동하는 실패다. 초안에 실행 중 전용 도구를 노출한 것이 원인인지 가른다.

with-insert는 현행과 같은 도구 표면, draft-only는 plan_insert_step만 숨기는 후보다.
프롬프트·색인·단계 상한·초안 보호·되묻기 횟수는 동일하다. 숨긴 도구 이름을 직접
호출해도 수락하지 않으며 OpenCode와 같은 unavailable-tool 응답으로 재시도한다.
모델 측정 전 회귀 시험으로 이 차이와 기존 초안 보호를 확인한다.

웹→노션에서 설정당 20회, 같은 요청 표식을 공유하는 AB/BA 교대 비교를 한다.

합격률 외에 insert_step 호출·거절 후 누락, write 대체, 조사 중복, 빈 계획 즉답을 본다.
실행 중 재계획은 현재 같은 agent를 쓰므로 후보 채택 시 그 경로의 insert_step을
보존해야 한다. 제품 도구 표면과 탐침을 맞춘 회귀 시험과 실기기 확인 없이 반영하지 않는다.

## 반영한 변경과 검증

- plan.rs: 초안용 스키마를 전체 계획 RPC 스키마에서 분리하고 탐침 계약으로 내보낸다.
- opencode_config.rs: 초안 전용 agent는 네 계획 도구만 명시적으로 연다. 기존 재계획
  agent의 삽입 표면은 유지한다. 열린 도구 전체와 Drafting→Running 전이를 시험한다.
- chat.rs: 최초 계획과 초안 되묻기는 초안 agent, 실행 중 재계획은 기존 agent를 고른다.
- index-loop.mjs: 기본 guard는 제품 초안 계약을 읽는다. with-insert와 draft-only는
  이번 비교의 표면을 명시적으로 유지한다. 숨긴 이름의 직접 호출도 실제 unavailable로 처리한다.
- planIndexProbe.test.mjs: 실제 실패 인자, 초안 보호, 숨긴 도구 거절, 기본 제품 표면 일치.

cargo fmt --all → --check 통과. 현재 공유 트리에서 Core 전체 1871 passed, 0 failed,
1 ignored. 전체 src/lib JS 시험과 tsc --noEmit 통과. Core 수에는 다른 세션이 추가한
직접 호출·거절 관련 시험도 포함되므로 모두 이번 변경의 시험이라고 세지 않는다.

## 병행 변경과 제품 고리 일치

작업 도중 다른 세션이 plan.rs와 chat.rs에 직접 색인 도구 호출 후 cannot_do를 한 번
되돌리는 변경을 추가했다. e6afe8bb에는 그 변경과 함께 제가 작성 중이던 두 파일의
초안 agent 선택·스키마 분리도 포함됐다. 이력을 되돌리지 않고, 남은 설정과 탐침·시험을
완성했다. os_keychain.rs 등 다른 세션의 남은 변경은 커밋에 담지 않는다.

기본 guard 탐침에는 e6afe8bb의 거절 응답도 Rust에서 생성해 동기화했다. 이번 120개
기록에는 cannot_do 호출이 없었다. 후보 60개는 현재 제품 guard로 별도 재생하여
모델에 보낸 모든 요청(도구 목록·반환 응답 포함)과 최종 steps·ended가 동일함을 확인했다.
with-insert와 draft-only는 비교 당시 고리를 재현하는 명시적 변형이다. 제품 기본값은
guard이며, 과거 변형을 현재 제품이라고 부르지 않는다.
