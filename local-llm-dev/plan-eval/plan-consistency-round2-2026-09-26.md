## 먼저 세운 가설과 측정

수정 후 실기기 ses_f2311fc3affeAN8b31tAebiqdP에서 계획 단계의 직접 webfetch 호출이
OpenCode invalid로 바뀌고, 모델은 인터넷 기능이 없다고 오해해 cannot_do로 끝냈다.
Core의 친절한 직접 호출 안내에 도달하기 전의 오류이므로 Core 문구만 바꾸지 않는다.

가설 1: 6,584자 색인의 반복된 플러그인 소유자·한글 별칭이 계획 내용을 흐린다.
같은 소유자 목록을 묶음 제목으로 옮겨 4,792자로 줄인다. 도구 이름·설명·순서·소유자가
모두 같은지 왕복 비교 시험으로 고정했다. 길이와 소유자 표기 위치가 함께 바뀌므로
순수한 토큰 수 효과라고 단정하지 않는다. 계획 고리와 도구 개수는 그대로다.

가설 2: 단계당 한 도구라는 프롬프트/실행 구조와 최대 4개를 허용하는 스키마/검증이
어긋난다. 첫 비교의 현행 7회차에서 실제로 다음 인자를 수락했다.

~~~json
{"title":"확인한 React 최신 버전 정보를 노션 페이지에 정리한다","tools":["write","notion-create-pages"]}
~~~

send_opencode_step_turn은 첫 도구로 agent를 고른다. 이 예에서는 write agent가
선택되어 노션 껍데기가 열리지 않는다. 따라서 계획에 적힌 작업과 실행 표면이 다르다.
색인은 원래대로 두고 스키마와 normalize_tools의 상한만 4 → 1로 바꿔 비교한다.
경로를 주장하는 프롬프트 문장이나 도구 추가, 실행기 변경은 하지 않는다.

두 비교 모두 web-to-notion 하나에 설정당 20회, 같은 회차 표식으로 AB/BA 교대했다.
회차 표식은 요청 구별용 UUID이며 모델의 난수 seed를 같게 고정한 것은 아니다.
선택 기준은 합격률만이 아니라 실제 어긋난 단계·호출·종료 경로다.

## 한 도구 계약

MAX_TOOLS_PER_STEP을 1로 맞췄다. add_step과 insert_step의 스키마와 공통 정규화가
같은 상수를 쓴다. 서로 다른 두 도구는 초안을 바꾸기 전에 거절하고 단계를 나누도록
기존 오류 경로로 돌려준다. 같은 도구 이름의 중복은 종전처럼 하나로 정규화한다.

실제 탐침 인자를 쓴 Rust 회귀는 거절 후 단계 수·순서·앞 단계 참조를 보존하고,
노션 도구만 가진 별도 단계를 추가해 확정할 수 있음을 확인한다. 실행 중 삽입도
같은 계약을 확인한다. 주석에는 날짜와 원본 요청 세션 ses_f23842cd6 및 실제 인자를
얻은 GPU 탐침 회차를 구분해 남겼다. JS 회귀는 실험용 single 대신 제품 기본 guard로
거절·복구를 확인한다. 계획 도구 표면 사본은 Rust 계약 시험으로 갱신했다.

| --- | --- | --- | --- | --- |
| 웹→노션, 각 20회 | 11 / 9 | 15 / 5 | 67 / 70 | 사용자 지시로 미측정 |
| 노션 검색·수정, 각 20회 | 18 / 2 | 18 / 2 | 74 / 68 | 사용자 지시로 미측정 |
| 로컬 조회, 각 20회 | 19 / 1 | 20 / 0 | 43 / 44 | 사용자 지시로 미측정 |

웹의 1개 상한 실패는 webfetch만으로 조기 확정 2회, 노션 대신 write 3회다.
그중 한 예는 webfetch가 셋으로 늘어난 뒤 write로 끝났다. 원래 증상인 조사 중복과
노션 누락은 해결하지 못했다. 4개 상한 실패는 노션 누락 8회와 단계 없는 즉답 1회다.
웹 single 1회차는 webfetch와 read를 함께 선언했다가 거절받고 webfetch 단계와 노션
단계로 고쳤다. 노션 수정 single 16회차는 fetch+update 거절 뒤 update로 고쳤고,
19회차는 fetch와 update를 두 단계로 나눴다. 이런 복구 사례는 있지만 작은 표본의
성공률로 설정을 고르거나 11/20 → 15/20 전체를 거절 덕분이라고 해석하지 않는다.
반영 근거는 실행 표면과 맞지 않는 계획을 수락하던 재현 가능한 계약 결함이며,
전체 의미적 일관성 향상을 주장하지 않는다.

노션 수정 실패는 4개 상한에서 단계 없는 즉답과 파일 edit 선택 각각 1회,
1개 상한에서 본문 수정 대신 댓글 도구와 파일 edit 선택 각각 1회다. 로컬 조회 대조는
read 단계 뒤 잘못된 거절 1회였고 1개 상한은 모두 계획을 확정했다. 세 과제 모두 수행
가능하므로 정직한 거절로 인정한 시행은 없다.

두 후보 실험과 반대 과제를 합친 160개 기록을 최종 탐침으로 재생하여 steps와 ended가
모두 동일함을 확인했다. 원래 묶음 실험의 guard는 4개 상한이었으므로 재생 시
four-tools로 명시했다.

## 실기기와 검증

수정 후 세션 ses_f228e4483ffe2SVyfXQS0NAKfo를 지정된 54181 격리 백엔드에서
같은 요청과 GPU로 실행했다. 계획은 webfetch → notion-create-pages → notion-update-page
3단계로 확정됐다. 노션 목적지는 들어갔지만 생성과 서식 수정이 분리된 계획이며,
이번 한 판으로 일관성이 확보됐다고 말하지 않는다.

실행은 웹 조회 3회 뒤 노션 스키마 검색까지 진행했다. 모델이 plugins_call_tool 대신
없는 notion-call_tool을 불러 invalid가 났고, 다음 단계는 update 스키마 조회 후 끝났다.
실제 plugins_call_tool 호출은 0회로 노션 생성·수정은 수행되지 않았다. 테스트 작업
폴더에도 파일이 생기지 않아 되돌릴 결과물이 없다. 세션은 completed로 끝났지만
최종 답변에도 노션 저장 실패가 적혀 있다. 업무 전체 성공으로 기록하지 않는다.

계획 단계에는 복수 도구가 없었다. 이번 회귀는 탐침에서 관찰한 복수 도구 인자를
고정하며, 실기기는 변경 후 계획→순차 실행→종합 경로를 확인한 것이다. 실행 도구
이름 오류와 invalid 메시지가 다음 단계에 전달된 문제는 범위 밖으로 남긴다.
웹 조회 내용 자체의 최신성은 이번 계획 평가의 검증 항목이 아니다.
