# 계획 수립 평가셋

로컬 모델에게 **계획을 어떤 모양으로 받아야 하는가**를 실측으로 정한 기록이자, 그 결론이
깨지지 않았는지 다시 재는 자리다. 작업 9.8에서 회귀 시험으로 고정했다.

## 왜 필요한가

도구 묶음 전환으로 "노션이냐 셸이냐"는 갈랐지만 그 안이 45개다. 낱말 분류기는 거기까지
못 간다. 단계마다 자기 도구를 선언하게 하면 도구 수가 턴이 아니라 **단계 단위**로 줄어드는데,
그러려면 모델이 계획을 제대로 내야 한다. 그게 되는지를 먼저 쟀다.

## 재는 법

Ollama 가 떠 있어야 한다. 온도·num_ctx 는 건드리지 않는다 — 모델 Modelfile 에 이미 박혀
있고, 권장값 아래로 내렸다가 51,730자 반복 붕괴를 본 적이 있다.

```sh
node local-llm-dev/plan-eval/plan-loop.mjs qwen3.5-gpu-128k:latest
node local-llm-dev/plan-eval/plan-loop.mjs gpt-oss-cpu-low:latest
```

회차마다 프롬프트에 무작위 표식을 붙인다. 안 붙이면 프롬프트 캐시가 결과를 부풀린다.
**두 모델을 동시에 돌리지 않는다** — 서로의 모델을 메모리에서 내쫓아 측정이 망가진다.
그래서 이것은 한 명령으로 도는 시험이 아니라 모델마다 따로 부르는 절차다.

기준선 아래로 떨어진 과제가 하나라도 있으면 `plan-loop.mjs` 는 **exit 1** 로 끝나고 무엇이
얼마나 떨어졌는지 마지막에 모아 찍는다. 통과하면 `기준선 미달 없음` 한 줄이다.
`REPEATS` 로 시행 수를, `ONLY_TASK` 로 과제 id 를 골라 좁힐 수 있다.

관문은 **시행 한 번만큼의 여유**를 두고 견준다. 3회 표본에서 한 번 어긋나면 비율이 1.00 에서
0.67 로 떨어지는데, 1.00 으로 적힌 과제도 다음 표본에서 한 번쯤은 흔들린다 — 이 절을 쓰면서
GPU `cross-boundary` 와 `다단계` 가 차례로 그랬다. 여유 없이 견주면 미달 줄이 늘 떠 있어
아무도 보지 않게 되므로, 이 관문이 잡는 것은 **한 시행을 넘는 하락**이다. 흔들린 것은
`한 시행 안쪽 흔들림` 으로 찍히고 exit 는 0 이다. 드리프트를 잡고 싶으면 `REPEATS` 를 올린다 —
여유는 `1/REPEATS` 라 시행을 늘리면 같이 좁아진다.

채점 규칙 자체는 Ollama 없이 도는 단위 시험이 고정한다 — `src/lib/planEvalScoring.test.mjs`
(저장소 표준 `node --test src/lib/*.test.mjs` 에 딸려 돈다). 거기가 깨지면 기준선 수치의
뜻이 바뀐 것이므로 기준선도 다시 재야 한다.

## 기준선 (2026-09-25)

`plan-loop.mjs`, 과제 여섯 × 3회. 기준선은 목표가 아니라 **바닥**이다.

| 과제 id | 과제 | GPU 9.7B | CPU 20.9B |
| --- | --- | --- | --- |
| `simple-create` | 단순 생성 | 3/3 | 2/3 |
| `multi-step` | 다단계 | 3/3 | 2/3 |
| `impossible-plan` | 불가능 | 3/3 | 3/3 |
| `read-only` | 읽기만 | 3/3 | 1/3 |
| `cross-boundary` | 경계 넘기 | 3/3 | 2/3 |
| `impossible-physical` | 불가능(바깥일) | 3/3 | 3/3 |

앞의 셋은 03c189ad 에서 온 값이고 뒤의 셋은 같은 날 새로 쟀다. 표본의 전형값을 적는다 —
한 시행만큼의 흔들림은 위의 여유가 받는다. CPU `read-only` 1/3 이
눈에 띄는데 어긋난 두 건은 계획이 나쁜 것이 아니라 **모양이 깨진 것**이다(`모양깨짐` 2) —
계획 품질이 아니라 도구 호출 자체가 무너졌다. 올리는 것은 이 시험이 아니라 프롬프트·모델
쪽 일이라 값은 그대로 바닥으로 적었다.

CPU `cross-boundary` 의 어긋난 한 건은 `notion-create-page` 라는 **없는 이름**이었다.
목록에 있는 것은 `notion-create-pages` 다 — 복수형 하나 차이로 지어낸 이름이 나온다.

## 관문이 빨갛게 나오면

**먼저 다시 잰다.** 이 평가셋은 n=3 이라 관문은 드리프트 감지기가 아니라 **붕괴 감지기**다.
같은 모델·같은 과제를 세 표본 잰 실측이 그것을 그대로 보여 준다 (2026-09-25, GPU):

| 과제 | 표본 1 | 표본 2 | 표본 3 |
| --- | --- | --- | --- |
| 다단계 | 3/3 | 2/3 | 3/3 |
| 경계 넘기 | 3/3 | 2/3 | 2/3 |
| 불가능 | 3/3 | 3/3 | **1/3** |

한 시행 여유가 2/3 을 흔들림으로 받아 넘기고, 1/3 에서 미달로 울렸다. 관문은 제 일을 했지만
그 1/3 이 회귀인지 운인지는 한 표본으로 알 수 없다. 그러니 순서는 이렇다 —

1. `REPEATS=9` 로 그 과제만 다시 잰다(`ONLY_TASK=impossible-plan`). 여유가 1/9 로 좁아지므로
   흔들림과 하락이 갈린다.
2. 다시 재도 낮으면 그때 원인을 본다. `어긋난 예` 에 찍히는 이유 줄이 어디가 무너졌는지
   말해 준다 — 없는 도구 이름인지, 단계 수인지, 거절해야 할 것에 계획을 세운 것인지.
3. 프롬프트나 모델이 바뀌어 값이 진짜로 옮겨갔으면 `BASELINES` 를 고치고 **왜 옮겼는지
   주석으로 남긴다.** 빨갛다고 숫자만 내리는 것은 관문을 끄는 것과 같다.

## 각 스크립트가 무엇을 정했나

`plan-probe.mjs`·`plan-shapes.mjs`·`callcount.mjs` 는 2026-09-27 에 지웠다 — 계약 기반 탐침
(`index-loop.mjs`, `fixtures/planning-contract.json`)이 제품과 같은 문구·가드로 재므로 옛 탐침을
돌리면 제품과 다른 결함을 잡는다. 아래 기록은 그 시절 결론이고 코드는 git 이력에 있다.

`plan-probe.mjs` — 첫 탐색. 도구 호출 자체는 3/3 성공인데 인자 모양이 무너졌다. 여기서
"중첩이 문제"라고 결론 냈는데 **n=3 이라 틀린 결론이었다.**

`plan-shapes.mjs` — 반복을 붙여 세 모양을 비교했다. GPU 만 보면 셋이 비슷하다. **CPU 가
가른다.**

| 모양 | GPU | CPU |
| --- | --- | --- |
| A 중첩 객체 배열 | 6~8/9 | **0/6** |
| B 단계별 호출(평평) | 8~9/9 | 5/6 |
| C 문자열 배열 + 구분자 | 7/9 | 재지 않음 |

중첩이란 배열 안에 객체가 있고 그 안에 또 배열이 있는 것이다. 깨질 때는 배열이 통째로
문자열이 되거나 객체가 문자열로 무너져 `tools` 가 소실된다 — 어느 도구를 열지가 이 설계의
핵심인데 그것이 날아간다.

이 스크립트는 **모양과 타당성을 나눠 센다.** 모양만 보면 할 수 없는 일에 그럴듯한 3단계를
세운 것을 정상으로 센다. 그게 실제 사용에서 제일 아픈 실패다 — 단계가 다 "성공"하고
아무것도 안 된 채 끝난다.

`callcount.mjs` — 한 응답에 도구 호출이 몇 개 오는지. **두 레인 다 하나만 온다.** 그래서
여러 호출을 한 번에 받는 설계에 기대면 계획이 1단계로 잘린다. 계획도 실행도 고리여야 하는
이유가 이것이다.

`plan-loop.mjs` — 확정된 모양. `add_step` 하나마다 결과를 돌려주고 다음을 묻는다.
`cannot_do` 로 거절할 자리를 준다 — **없으면 불가능한 일도 0/6 으로 전부 계획을 지어냈다.**
거절할 방법이 없는데 "계획을 세우라"고 시켰으니 모델이 아니라 프롬프트 탓이었다.

## 확정된 계약

- 계획은 고리로 받는다: `add_step` 하나씩 → `finish_plan`
- 한 응답에 여러 호출을 기대하지 않는다
- 중첩 스키마를 쓰지 않는다
- 거절 도구(`cannot_do`)는 필수다
- 단계 번호는 우리가 매긴다 — 모델에게 "200과 300 사이" 산수를 시키지 않는다

## 채점기

`scorePlan`(`plan-tasks.mjs`)이 단계 수 범위·요구 도구·없는 이름 셋을 보고, 어긋났으면
**그 이유를 함께** 돌려준다. 이전 판은 기대 도구를 이름 하나로 박아 두어 같은 일을 다른
도구로 해낸 것을 어긋난 것으로 셌다(2026-09-25 CPU 다단계의 `notion-create-comment`).
이제 한 요구는 **동치 도구의 집합**이고 그중 하나만 쓰면 충족이다.

남은 한계는 둘이다. 단계의 **순서**와 목표 문장의 내용은 보지 않는다 — 순서가 뒤집힌
계획도 도구만 맞으면 타당으로 센다. 그리고 불가능 과제는 "단계 0개"로만 판정하므로
`cannot_do` 로 제대로 거절한 것과 도구 호출이 아예 무너진 것을 구별하지 못한다. 실제로
GPU `impossible-physical` 3/3 안에는 `모양깨짐` 1 과 `도구호출없음` 1 이 섞여 있었다.
고치려면 채점기가 고리의 종료 사유까지 받아야 하고, 그러면 불가능 과제의 기준선을 전부
다시 재야 한다 — 그래서 이번에는 한계로 적어 두고 두었다.

## 도구 색인 탐침 (`index-probe.mjs`) — 작업 9.10 착수 전 측정

계획 턴에 **도구 색인을 펼쳐 주고 한 단계에 도구 하나**로 계획시키면 맞는 도구를 고르는가.
기존 `plan-loop.mjs` 는 일곱 개짜리 카탈로그로 쟀다. 여기서 보는 것은 그보다 한 자릿수 큰
색인에서도 같은 고리가 서는가다.

```sh
node local-llm-dev/plan-eval/index-probe.mjs qwen3.5-gpu-128k:latest
node local-llm-dev/plan-eval/index-probe.mjs gpt-oss-cpu-low:latest
```

색인은 `tool-index.mjs` 가 만든다 — `id + 한 줄 설명`. 도구 집합이 같은 플러그인은 설명을
한 벌만 적는다(`notion-team`·`notion-personal` 는 45개가 정확히 겹친다). 카탈로그 고정본은
`fixtures/plugin-catalogs.json` 이고, 다시 뜨려면 개발 백엔드에서
`get_external_plugin_tools` 를 플러그인마다 받아 같은 모양으로 적는다.

**크기: 49개 · 6,104자 ≈ 2,035토큰.** 설명을 80자로 잘라도 이득이 없어(첫 문장이 이미 짧다)
그대로 쓴다.

### 기준선 (2026-09-26, n=4)

| 과제 | GPU | CPU |
| --- | --- | --- |
| `web-to-notion` 웹 조사 → 노션 작성 | 3/4 | 3/4 |
| `find-then-edit` 노션에서 찾아 고치기 | 4/4 | 4/4 |
| `local-read` 파일 읽기 | 4/4 | 4/4 (직접호출 3회 고침) |
| `pick-comment` 비슷한 이름 중 고르기 | 4/4 | 3/4 |
| `impossible` 도구 없는 일 거절 | 3/4 | 4/4 |

**결론: 도구를 알아보는 것은 된다.** 49개 색인에서 `notion-create-comment` 와
`notion-create-pages` 를 가르고, `notion-search → notion-update-page` 순서를 세운다.
남은 실패는 알아보기가 아니라 **조합**이다 — GPU 가 `webfetch, write` 로 계획해 노션 대신
파일에 쓴 자리가 그것이다.

### 이 탐침이 찾아낸 것

- **색인이 실행을 부른다.** 모델이 색인에 있는 `read` 를 계획 대신 곧바로 호출했다
  (`모양깨짐(read {"path":"package.json"})`, CPU `local-read` 0/4). 색인이 "이런 게 있다"와
  "지금 불러도 된다"를 흐린다.
- **프롬프트로 막으면 다른 쪽이 열린다.** "지금 이 목록의 도구를 부르면 안 된다"를 넣자
  직접 호출은 0이 됐지만 **할 수 있는 일까지 거절**하기 시작했다(`pick-comment` 2/4).
  역할만 설명하는 문장으로 되돌리니 직접 호출이 돌아왔다.
- **그래서 고리에서 고친다.** 색인 도구를 직접 부르면 실패로 세지 않고 "그건 add_step 으로
  적어라"를 돌려주고 다음을 묻는다. `local-read` 가 0/4 → 4/4 가 됐다. 배선(9.10)도 같은
  자리를 가져야 한다.
- **조종 도구 이름을 한 글자 틀린다.** GPU 가 `finiish_plan` 을 불렀다. 조종 도구 셋은 뜻이
  분명하므로 한 글자 차이까지 되돌린다 — 색인 도구 이름은 되돌리지 않는다. 그쪽은 틀리면
  다른 일을 하게 된다.
- **불가능 과제는 주어진 도구 기준으로 불가능해야 한다.** 첫 판의 "프린터로 인쇄"는 `bash`
  가 열려 있으면 불가능하지 않다 — GPU 가 셸로 계획한 것은 모델이 아니라 과제가 틀린 것이라
  지메일(플러그인 미등록·셸로 인증 불가)로 갈았다.
- **플러그인 설명이 계획을 움직인다.** `notion-get-tool-access` 를 첫 단계로 넣는 계획이
  반복해서 나왔다 — 노션 도구 설명 자체가 "먼저 get_tool_access 를 불러라"라고 적고 있기
  때문이다. 색인은 남이 쓴 글을 계획 프롬프트로 들여오는 자리다. 해롭지는 않았지만(읽기)
  배선할 때 알고 있어야 한다.

### 한글 표기의 출처 (2026-09-27, 9.12)

아래 절의 한글 표기는 처음엔 Rust 상수 사전(`PLUGIN_ALIASES`)에서 나왔다. 지금은 **플러그인마다
저장된 이름 목록**(`names`, 애드온 폼의 "다른 이름")에서 나오고, 사전은 등록 때 그 목록을 미리
채우는 씨앗일 뿐이다. 픽스처 `plugin-catalogs.json` 의 `names` 가 이 기계의 이행 결과와 같아
계약 색인은 바뀌지 않았다.

### 한글 표기를 색인에 넣는다 (2026-09-26)

사람은 "노션에 정리해줘"라고 적는데 색인의 이름은 `notion-create-pages` 뿐이었다. 그래서
계획이 "정리해서 저장"을 `write`(파일)로 읽었다. 플러그인 칸에 한글 표기를 함께 적는다 —
`- notion-create-pages (notion-team · 노션 | notion-personal · 노션): …`.

`web-to-notion`, GPU 20회:

| | 합격 | 없는 이름 되묻기 | 실패 종류 |
| --- | --- | --- | --- |
| 별칭 있음 | 18/20 | 1 | `webfetch,write` 둘 |
| 별칭 없음 | 14/20 | 4 | 말로만 약속 · 도구호출없음 · `webfetch,write,read` — 제각각 |

합격률만으로는 결정적이지 않다(p≈0.23). **남기는 근거는 실패 종류다.** 별칭 없이는 노션
자리가 파일 쓰기나 빈 계획으로 채워지고, 넣으면 실패가 한 종류로 줄어든다.

### 이 과제는 흔들린다 — n≤6 으로 설정을 가르지 마라

같은 코드로 GPU `web-to-notion` 이 한 판 10/10, 다음 판 3/6 이 나왔다. n=6 짜리 표 두 개를
나란히 놓고 "좋아졌다"고 적으면 거의 틀린다. 설정을 가를 때는 **과제를 하나로 좁혀
(`ONLY_TASK=`) n≥20** 으로 재고, 합격률이 아니라 **어긋난 예의 종류**를 먼저 본다.

### 버린 것: `webfetch` 설명에 "인터넷" 넣기

CPU 가 "인터넷에서 조사"를 `notion-search` 로 계획하기에 `webfetch` 설명을
`"인터넷의 웹 페이지를 가져온다. 바깥에서 알아봐야 하는 일은 이것으로 한다."` 로 바꿨다.
CPU `web-to-notion` 은 올랐지만(6/10 → 8/10) **옆이 무너졌다** — 같은 판에서
`find-then-edit` 6/6 → 3/6, `local-read` 6/6 → 4/6. 로컬 과제까지 빨아들인 것이다.
범위 절을 원래대로 둔 `"인터넷의 웹 페이지를 가져온다. 주소(URL)를 알고 있을 때 쓴다."`
로도 GPU 가 10/10 → 6/10 이었다. **되돌렸다.** 단어를 더하는 것과 경로를 주장하는 것은
다르고, 뒤엣것은 색인이 할 일이 아니다.

### 탐침이 배포본보다 엄해선 안 된다

없는 도구 이름을 만나면 탐침이 그 자리에서 run 을 끝내고 실패로 셌다. 배포본은
`normalize_tools` 가 **고칠 수 있는 오류**("'X'라는 도구는 없습니다. 쓸 수 있는 도구: …")를
돌려주고 다음을 묻는다. 맞추고 나니 GPU `local-read` 는 3번 되물은 뒤 6/6, `pick-comment`
는 6/6 이었다 — 계획을 못 세운 것이 아니라 한 번 되물으면 되는 일이었다. 되물은 횟수는
합격과 따로 적는다(`되물은 없는 이름 N`).

## 2026-09-27 web-to-notion 재측정 — 플러그인 이름 가드

실기기(M7 7.5)에서 노션 단계가 빠지거나 `write`(로컬 파일)로 잡히는 실패가 남아 `ONLY_TASK=web-to-notion REPEATS=20`
으로 두 레인을 쟀다.

| 판 | GPU | CPU | 실패 종류 |
| --- | --- | --- | --- |
| 가드 전 | 18/20 | 19/20 | GPU: "노션에 정리"에 `write` 2 · CPU: 같은 단계 중복 1 |
| 가드 후 | 18/20 | 17/20 | GPU: `notion-update-page` 선택 1 · 1단계만 세움 1 · CPU: 이른 finish 2 · 단계 중복 1 |

가드는 add_step 에서 제목이 플러그인의 등록 이름(예: 노션)을 말하는데 도구가 그 플러그인 것이 아니면
그 플러그인의 도구를 나열해 되묻는다(`pluginGroups`·`pluginMismatchError`). GPU 에서 4번 되물었고
4번 다 그 플러그인 도구로 고쳐 통과했다 — "노션 → write" 종류는 0이 됐다. 합격률은 그대로이고 CPU 의
두 건 차이는 가드가 한 번도 걸리지 않은 레인이라 흔들림으로 본다. 남은 종류(이른 finish·단계 중복·
1단계만)는 다음 회차 몫이다.
